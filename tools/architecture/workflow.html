bc_dev_permits

Development Permit Pipeline

How a development application travels from four BC municipal websites into one normalized dev_permit schema, then out to JSON, Postgres, and the map. The whole flow is driven by one CLI: python -m bc_dev_permits.dataset.

primary data path module call optional PDF enrichment (low-signal rows only)

1. Sources

Four municipalities on three platforms: CNV and Victoria publish HTML pages; Coquitlam and Maple Ridge expose ArcGIS REST services.

2. Harvesters

One module per city in harvesters/. HTML harvesters share pdf_enrich.py; ArcGIS harvesters share arcgis_common.py (session, paged query, centroid).

3. Parse

features.py turns prose and map attributes into schema fields deterministically, with no model on the common path. Every harvester scores and returns dev_permit rows.

4. Enrich (optional)

Rows with no units/storeys/area route through pdf_enrich.py to read their PDFs, via Ollama (predict.py) or Claude in-session. Deterministic HTML values always win; disagreements are logged as conflicts.

5. Orchestrate

dataset.py is the CLI entry point: it picks the harvester, applies --address, optionally enriches, and writes the chosen output.

6. Output & view

Rows land as data/processed/*.json, in Postgres via load.py, or on stdout. The JSON feeds the QA viewer and the BC Permit Atlas dashboard.

config.py supplies every harvester's URLs, Ollama settings, cache and DB paths; references/schema.sql defines the dev_permit table plus its occupancy, milestone, and document child tables. Provenance travels with every field (extraction_method, per-field methods, extraction_confidence, needs_review) so a value can always be traced back to its source.
